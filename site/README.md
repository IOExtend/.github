# IOExtend Web

Локальная сборка инструментов IOExtend для просмотра, экспорта и понижения версии Revit. Выберите RVT через диалог или перетащите его на любую вкладку. Вкладки используют один исходный файл. 3D-сцена RVT или NWC подготавливается при открытии вкладки «Просмотр». Ракурс сохраняется при возвращении к сцене. Форматы, доступные для выбора и обработки, зависят от вкладки.

Язык сайта и встроенного просмотрщика выбирается в шапке. В режиме «Авто» используется первый поддерживаемый язык из списка браузера. Если подходящего языка нет, используется английский. Ручной выбор сохраняется в браузере. При смене языка 3D-просмотр заново открывается из подготовленных данных с начальным ракурсом. Автономный HTML IOViewer имеет собственный переключатель и работает без сети.

Во время открытия видны текущий этап, примерный процент и время ожидания. Для RVT дополнительно видны счётчики
распакованных потоков, проходов разбора, блоков при восстановлении геометрии, блоков записей и имён,
прочитанных байтов и элементов, для которых построены сетки. При подготовке просмотра видны счётчики записанных
треугольников, обзорных страниц на каждом уровне и обработанных элементов. Веса этапов используются для оценки общего хода
работы. Обработку можно отменить кнопкой «Отменить». Замер `ioextend:first-frame` в браузере идёт от начала открытия модели во «Просмотре» до первого отрисованного кадра.

## Запуск

Соберите проект с .NET 10 SDK и запустите статический сервер в папке с результатом.
Локальная сборка использует ветку `codex/rvt-segment-spooling` с чтением сегментов через временное хранилище. Чтобы подключить постраничный просмотр, подготовьте зависимости Node.js в исходниках IOViewer и передайте обе папки при сборке. [RvtIO PR #308](https://github.com/IOExtend/RvtIO/pull/308) · [IOViewer PR #81](https://github.com/IOExtend/IOViewer/pull/81)
[Прогресс чтения](https://github.com/IOExtend/RvtIO/pull/304), [ограничение временных результатов декодирования](https://github.com/IOExtend/RvtIO/pull/305), [чтение RVT из потока](https://github.com/IOExtend/RvtIO/pull/306), [чтение страниц RVT без копии потока](https://github.com/IOExtend/RvtIO/pull/307).

```powershell
dotnet publish -c Release -o publish-web -p:RvtIOProgressSource=/path/to/RvtIO -p:IOViewerSource=/path/to/IOViewer
python -m http.server 8976 --bind 127.0.0.1 --directory publish-web/wwwroot
```

Откройте [локальную страницу](http://127.0.0.1:8976/). Для GitHub Pages каталог `publish-web/wwwroot` можно использовать как артефакт публикации. В нём должны остаться `index.html` и папка `_framework`. [Документация GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

Для AOT-сборки разработчика используйте .NET 11 SDK с рабочей нагрузкой `wasm-tools`. Откройте статический сервер в каталоге `publish-web-aot/wwwroot`.

```powershell
dotnet publish -c Release -o publish-web-aot -p:IOExtendAot=true -p:RvtIOProgressSource=/path/to/RvtIO -p:IOViewerSource=/path/to/IOViewer
```

Профиль `-p:IOExtendPooledGc=true` включает экспериментальное групповое выделение блоков Mono SGen в
однопоточной сборке .NET 11 WebAssembly. Пул включается при сборке записей RVT и остаётся активным при
финализации. Для этого профиля добавьте флаг к команде AOT-сборки. Посетитель открывает её как обычную
статическую страницу в Chromium.

При сравнении с исходниками без API временного хранения из #308 передайте `-p:RvtIOPartitionScratch=false`. В этом режиме RvtIO держит распакованные сегменты в памяти, а IOViewer может записать готовую сцену в страницы. Для крупных RVT используйте сборку с временным хранилищем.

Для небольших RVT профиль `IOExtendFastReader` собирает отдельный однопоточный AOT-воркер с полной обрезкой
неиспользуемого кода. Воркер читает RVT и возвращает автономный HTML. Основная сборка обслуживает NWC,
постраничный просмотр и резервное открытие RVT. Для сравнения с нативным экспортом передайте ту же ревизию
IOViewer. Используйте отдельный каталог промежуточных файлов для каждого профиля, чтобы компоновщик применил
параметры обрезки. В чистом RvtIO `d6e7d8b` расчёт количеств дверей и окон ожидает фоновую задачу.
Однопоточный WebAssembly в этом месте выдаёт `Arg_PlatformNotSupported`, и сайт открывает файл повторно.
Для быстрого читателя подготовьте отдельный каталог с этой ревизией и исправлением браузерного пути.
Команды подготовки исходников рассчитаны на новый каталог. [RvtIO #310](https://github.com/IOExtend/RvtIO/pull/310)

```powershell
$readerCore = "../artifacts/fast-reader-src"
$main = "d6e7d8b8b447a18750c4e75ab03487e24b75c541"
$browserFix = "74d2c997bf80e7a923e6036f98a1fbbf70141e4a"
git init $readerCore
git -C $readerCore remote add origin https://github.com/IOExtend/RvtIO.git
git -C $readerCore sparse-checkout set src/RvtIO src/RvtIO.Scene
git -C $readerCore fetch --no-tags --depth=2 --filter=blob:none origin $main $browserFix
git -C $readerCore checkout --detach $main
git -C $readerCore cherry-pick --no-commit $browserFix
```

В проверенной паре сборок веб-читатель и нативный экспортёр используют IOViewer
`b12b27a5708b0b08c2a241311ac2254cac31a984`. Передайте каталог этой ревизии в `IOViewerSource`. [IOViewer #82](https://github.com/IOExtend/IOViewer/pull/82)

```powershell
dotnet publish IOExtend.Web.csproj -c Release --artifacts-path ../artifacts/fast-reader -o ../artifacts/fast-reader/publish -p:IOExtendFastReader=true -p:IOExtendPooledGc=true -p:RvtIOPartitionScratch=false "-p:RvtIOProgressSource=$((Resolve-Path $readerCore).Path)" -p:IOViewerSource=/path/to/IOViewer
node prepare-web-release.mjs publish-web-aot/wwwroot --fast-reader ../artifacts/fast-reader/publish/wwwroot
```

Рабочая страница выбирает быстрый воркер для RVT до 50 МиБ при изоляции источника, от 8 ГиБ памяти по данным браузера
и от пяти логических процессоров. Воркер формирует автономную сцену из того же исходного RVT. Страница повторяет
открытие через основной постраничный путь при ошибке, после 25 секунд без продвижения чтения или после 25 секунд
ожидания первого кадра готовой сцены.
Выбор файла и отмена остаются общими для обоих режимов.
На статическом хостинге без серверных заголовков изоляции релиз с быстрым читателем использует локальный
Service Worker. При первом посещении он перезагружает страницу, пока посетитель ещё не начал выбирать файл.
Аргумент со статическим URL без заголовков в `fast-reader-smoke.cjs` проверяет этот запуск в отдельном контексте Chromium.

Экспериментальный профиль `-p:IOExtendThreaded=true` собирает AOT-версию на .NET 10 SDK с `wasm-tools` и исходниками RvtIO из #311 поверх #308. Передавайте его вместе с `-p:IOExtendAot=true` и `-p:IOExtendFallbackSite=/path/to/publish-web-aot/wwwroot`. Для обеих сборок используйте одну ревизию IOViewer. Профиль декодирует геометрию в четырёх потоках или меньше и применяет результаты в порядке записей RVT. [RvtIO #311](https://github.com/IOExtend/RvtIO/pull/311)

На хостинге с заголовками `Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: require-corp` доступна общая память WebAssembly. Файлы `.mjs` должны отдаваться с типом JavaScript. Для GitHub Pages разместите эту сборку в отдельном каталоге, например `parallel/`. При первом визите Service Worker добавит заголовки в пределах этого каталога и перезагрузит страницу, если посетитель ещё не начал выбирать файл. Без изоляции сайт использует однопоточную сборку. [Поддержка потоков в .NET WebAssembly](https://github.com/dotnet/runtime/blob/main/src/mono/wasm/features.md#multi-threading)

На запуск каждого обработчика просмотра отводится до минуты, пока среда WebAssembly готовится к чтению файла. Если многопоточный воркер зависнет при запуске или завершится со сбоем WebAssembly, сайт один раз повторит открытие того же локального файла в однопоточном режиме. Прогресс показывает повторное открытие, а следующие модели в этой вкладке сразу идут в однопоточный обработчик. Если он завершится ошибкой или зависнет на запуске, сайт покажет сообщение и снова позволит выбрать файл. Ранее открытая модель останется доступной. После запуска время чтения модели не ограничено. Данные модели обрабатываются локально.

Переменная `IOEXTEND_REQUIRE_THREADS=1` включает проверку изоляции и общей памяти WebAssembly в `smoke.cjs`. Команда `node reader-recovery-smoke.cjs <isolated-url> <rvt> [unisolated-url]` проверяет восстановление после сбоя WebAssembly, зависание при запуске обоих воркеров, продолжение чтения после истечения минуты, отказ резервного воркера, отмену и прямую загрузку без изоляции.

## Экспорт и даунгрейд

После публикации сайта соберите браузерные обработчики в тот же `wwwroot` с .NET 10 SDK. Для экспорта используйте ту же ревизию RvtIO, что и для просмотра, и NwcIO `d2c8469` (0.17.0). Для даунгрейда использовалась ветка `feat/revit-downgrade` RvtIO, коммит `7936c6e`.

```powershell
./operations/Publish.ps1 -Site ./publish-web/wwwroot -Build ./obj/site-tools -RvtIOProgressSource /path/to/RvtIO-export -NwcIOSource /path/to/NwcIO -DowngradeSource /path/to/RvtIO-downgrade
```

С .NET 11 SDK и рабочей нагрузкой `wasm-tools` к команде можно добавить `-ExportLargeHeap`. Этот профиль собирает обработчик экспорта с верхней границей линейной памяти почти 4 ГиБ.
Для сравнительной сборки экспорта с исходниками из #310 передайте `-RvtIOPartitionScratch:$false`. Доступные счётчики этапов зависят от API выбранного ядра.

Добавьте `-IOViewerSource /path/to/IOViewer`, чтобы использовать актуальную сборку автономного просмотрщика в HTML-экспорте RVT, RFA, NWC и NWD. Перед сборкой выполните `npm ci` и `npm run build` в каталоге `src/IOViewer/Viewer`. Прежний HTML Navisworks доступен отдельно среди дополнительных форматов.

Доступные форматы зависят от исходного файла. За один запуск можно получить несколько файлов. Дополнительные результаты Navisworks, например TimeLiner, требуют соответствующих данных в модели. Повторное сохранение Navisworks в NWC использует собственный формат записи NwcIO и отклоняет модели с линейными сетками. Для даунгрейда выберите исходный RVT или RFA. Сайт определит версию из потока `BasicFileInfo` и предложит более ранние версии из диапазона 2020–2026. RvtIO проверяет схему модели после запуска и создаёт отдельную копию с отчётом. Даунгрейд экспериментальный.

Обработчики читают исходные файлы по диапазонам. Для RVT и RFA используется `MONO_GC_PARAMS=soft-heap-limit=512m`, чтобы Mono раньше освобождал временные данные. Выходной файл собирается в памяти браузера. Предельный размер зависит от модели и доступной памяти.

Во время экспорта и даунгрейда видны этап, время обработки и объём чтения и записи. Счётчики ввода и вывода учитывают повторные обращения к файлу. Процент этапа появляется, если ядро сообщает выполненный и общий объём работы. При экспорте в несколько форматов отдельно видно, сколько обработок завершилось.

Браузерная проверка запускается через `node operations-smoke.cjs <локальный URL> <пример.nwc> <пример.rvt> <целевая-версия> [<пример-для-даунгрейда.rvt>]`. Она проверяет этапы и отмену, скачивание файлов, список версий, отчёт и отказ при повреждённых метаданных.
Проверка `node localization-smoke.cjs <локальный URL> <пример.nwc> [<пример.rvt>]` проверяет словари, режим «Авто», сохранение выбора, встроенный просмотр и скачанный HTML без сети.

Файлы в `wwwroot/profiles` содержат только таблицу классов, архивный заголовок и поля версии и сборки. Генератор в `operations/profile-tool` извлекает их из файлов целевых версий и сверяет заголовок со схемой. Полная модель и путь последнего сохранения в профиль не попадают.

При публикации интерфейс и загрузчики WebAssembly получают адреса с отпечатками содержимого. `prepare-web-release.mjs` записывает ресурсы до обновления `index.html`. Проверка `node release-smoke.cjs <wwwroot>` воспроизводит смешивание разметки и старых стилей на прогретом кэше и проверяет обычную перезагрузку.

## Как это работает

Весь разбор RVT и NWC и построение сцены должны выполняться в браузере пользователя. Посетителю должно
быть достаточно открыть страницу и выбрать файл. GitHub Pages используется для раздачи файлов приложения.
Модели RVT размером порядка 300 МБ и выше входят в целевой сценарий и требуют проверки на реальных проектах.

Браузер запускает RvtIO.Scene или NwcIO.Scene в отдельном Web Worker через .NET WebAssembly. Адаптер формирует IOScene, а IOViewer рендерит результат через WebGL 2. Файл модели остаётся в браузере. Для RVT с поддержкой OPFS ядро читает и пишет временные данные порциями. Однопоточная сборка с `IOExtendPooledGc=true` использует общий буфер до 512 МиБ вне линейной памяти WebAssembly. Поток, исчерпавший общий лимит, сохраняется в OPFS и продолжает работать с диска. Если браузер не поддерживает расширяемые буферы, оба потока сразу работают через OPFS. После сборки записей Revit временный поток сегментов освобождается перед построением сеток.

В сборке с исходниками IOViewer отдельный рабочий процесс преобразует треугольную сцену RVT в страницы геометрии и свойств. Перед передачей файла этому процессу читатель записывает его в OPFS. IOViewer запрашивает нужные диапазоны из локальных файлов пакета. Промежуточные файлы удаляются после построения страниц. Страницы остаются доступны до замены или закрытия модели. При отмене или ошибке удаляется папка текущего открытия. При следующем открытии сайт очищает оставшиеся папки, которые не используются другими вкладками.

До первого кадра новый фрейм просмотра остаётся прозрачным и недоступным для взаимодействия. Он находится в области просмотра, чтобы Chromium мог вызвать `requestAnimationFrame` внутри изолированного фрейма.

Для RVT сборщик мусора Mono настроен запускаться раньше через `MONO_GC_PARAMS=soft-heap-limit=512m`. Это порог для сборки мусора. Фактическое потребление памяти может быть выше.

Прототип обрабатывает одну модель за раз. Web Worker даёт .NET доступ к выбранному файлу диапазонами
по 512 КиБ для RVT и по 64 КиБ для NWC с кэшем до 16 МиБ. Пиковая память зависит от распакованных потоков, сложности геометрии
и временных данных ядра. При ошибках декодирования интерфейс сообщает, что часть элементов может отсутствовать.

У штатной сборки верхняя граница линейной памяти WebAssembly составляет 2 ГиБ. Для испытаний больших RVT
используется также AOT-сборка с границей почти 4 ГиБ. Измерения ниже относятся к указанным версиям прототипа.

## Проверка больших файлов

На локальных образцах браузер отрисовал постраничную геометрию, открыл свойства элементов и освободил временные данные после отмены. Синтетический RVT-контейнер на 10,01 ГиБ для проверки больших смещений сохранил исходную геометрию контрольной модели. Сложность реальной модели определяет расход памяти независимо от размера входного контейнера.

## Браузерная проверка

С установленным в среде Node.js пакетом Playwright запустите тест и передайте пути к локальным образцам. Тест проверяет перетаскивание, диалог выбора, замену и отмену, ошибки ввода и рендеринг обеих моделей.

```powershell
node smoke.cjs http://127.0.0.1:8976/ path/to/sample.rvt path/to/sample.nwc
```

Установите `IOEXTEND_REQUIRE_PAGED=1`, чтобы тест потребовал постраничный рендеринг для треугольной модели RVT.
Для сборки с `-p:RvtIOPartitionScratch=false` задайте `IOEXTEND_RVT_PARTITION_SCRATCH=0`, чтобы проверка учитывала набор событий прогресса этой версии ядра.

Для замера полного кадра подготовьте релиз с быстрым читателем и откройте его через локальный HTTP-сервер с
`Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: require-corp`. Для нативного контроля
передайте чистый RvtIO `main` и ту же ревизию IOViewer, что использует сайт. `NativeHtmlExport` читает исходный
RVT через `RvtSceneReader.Read` и записывает автономную сцену через `HtmlViewerExporter.Export` в новый файл.
В JSON-результате `readMs` включает чтение и построение сцены, а `exportMs` также включает запись и закрытие
HTML. Запускайте нативный и браузерный замеры последовательно.

```powershell
dotnet build ../tools/NativeHtmlExport -c Release --artifacts-path ../artifacts/native -p:RvtIOSource=/path/to/clean/RvtIO -p:IOViewerSource=/path/to/IOViewer
dotnet ../artifacts/native/bin/NativeHtmlExport/release/NativeHtmlExport.dll path/to/racbasicsampleproject.rvt path/to/native-export.html
node first-frame-smoke.cjs http://127.0.0.1:8976/ path/to/racbasicsampleproject.rvt path/to/native-export.html
```

Проверка запускает новый Chromium и передаёт RVT в обычное поле выбора файла. `viewerReadyMs` показывает время
до подтверждения рендера и показа iframe на странице. `firstFrameMs` измеряется от события выбора файла
до второго `requestAnimationFrame` после появления iframe. Между этими вызовами Chromium может вывести сцену
на экран. Проверка сверяет состав сцены, свойства, контрольную геометрию и единственную загрузку WASM
быстрого читателя. Время записи нативного HTML замеряется отдельно. Результаты описаны в [аудите](AUDIT.md).
